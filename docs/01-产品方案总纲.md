# 弹阅：桌面微阅读工具产品方案总纲

版本：0.1
日期：2026-08-27
状态：产品方向已明确，纵向样板已实现

## 一、产品结论

弹阅不是传统电子书阅读器，也不只是 AI 摘要工具，而是一款：

> 面向上班族的桌面微阅读工具，把一本书拆成每天几次、每次几十秒到一分多钟可以读完的完整片段，通过不打断工作的桌面浮窗，帮助用户持续读下去。

最重要的一句话是：

> 借用广告弹窗的触达能力，但绝不能带来广告弹窗的侵扰感。

产品成败不取决于“支持多少格式”，而取决于四个问题：

1. 一段内容是否足够短，同时意思完整。
2. 弹窗什么时候出现，才不会令人厌烦。
3. 用户产生兴趣后，能否无阻力继续读。
4. 用户不想读时，能否安静关闭，不制造负担。

## 二、完整产品表述

我们计划开发一款面向上班族的桌面微阅读软件。弹阅直接读取 TXT/Markdown，也接收外部 Agent 将 EPUB、PDF、DOCX 或网页转换后的标准 `.tanyue.json` 包。系统严格复核原文、来源锚点、顺序和覆盖率，再把内容作为 20～90 秒可读完的“微阅读片段”呈现。

每个片段保留完整原文及其在原书中的位置，不以 AI 摘要替代原文。对于较长或结构不清晰的内容，系统可以调用外部大模型，生成简短标题、上文承接和一句话解释，帮助用户快速进入语境。

用户可设置工作日、提醒时段、每日阅读数量、弹窗停留时间和勿扰时间。软件常驻系统托盘并支持开机启动，到达阅读时间后，以不抢占键盘焦点的桌面浮窗展示下一段内容。

用户可以直接阅读后等待弹窗自动关闭，也可以选择“读完下一段”“稍后提醒”“今天暂停”或“继续阅读”。点击继续阅读后，会展开简洁的连续阅读面板；收藏和笔记留在完整阅读界面，不挤占微读弹窗。

软件记录每个片段的来源位置、展示次数、阅读状态和整本书进度，在电脑重启、休眠或软件升级后仍能准确接续下一段内容。

产品目标不是替代 Kindle、Calibre 等完整阅读器，而是解决上班族“没有整块时间打开书，但每天可以读几次一分钟内容”的问题。

## 三、产品定位

### 3.1 它是什么

> 桌面微阅读习惯引擎。

用户不必每次主动打开软件，而是内容在合适的时间主动找到用户。

### 3.2 它不是什么

- 不是重型电子书管理器。
- 不是把整本书压缩成十条摘要的 AI 总结工具。
- 不是强迫用户打卡的学习软件。
- 不是复杂知识库或卡片复习系统。
- 不是书城和内容分发平台。
- 不是 DRM 破解工具。

首版不做书城、社交、排行榜、知识图谱、团队协作、移动端同步和扫描 PDF 大平台。

## 四、目标用户与场景

### 4.1 核心用户

- 电脑办公时间长的上班族。
- 明确想读书，但缺少连续阅读时间的人。
- 希望阅读经典、专业资料、行业报告、制度文件的人。
- 不愿被打卡和复杂学习系统绑架的人。

### 4.2 典型场景

- 上午工作进入稳定节奏后，右下角出现《道德经》一章。
- 用户读完后点“下一段”，连续读两章。
- 下午会议前系统检测到勿扰，不展示。
- 用户关闭一段，系统只记录“已展示”，不假装已经读完。
- 下班前用户打开今日回顾，查看收藏和未确认片段。

## 五、完整用户流程

```text
直接导入 TXT/Markdown，或让外部 Agent 生成标准包
        ↓
Agent 解析复杂格式、识别正文结构并生成来源锚点
        ↓
弹阅重新校验原文范围、顺序、哈希与 100% 覆盖率
        ↓
通过验证后原子入库；失败时返回明确原因
        ↓
可选：AI 生成标题、承接语和一句解释
        ↓
用户预览并确认拆分方式
        ↓
设置每日次数、时间窗口和停留时间
        ↓
软件进入系统托盘并按时弹出阅读卡片
        ↓
继续阅读 / 读完下一段 / 稍后提醒 / 今天暂停 / 自动关闭
        ↓
记录展示、确认阅读和整本书进度
        ↓
下一次从准确位置继续
```

### 5.1 第一次使用

首次打开不要展示复杂后台，只完成四步：

1. 拖入一本书、一个文档，或粘贴链接。
2. 自动解析并展示前 3～5 个阅读片段。
3. 用户选择约 30、60 或 90 秒。
4. 设置每天出现几次，以及在哪些时间段出现。

推荐默认值：

```text
工作日：周一至周五
阅读时段：09:30—11:30、14:00—17:30
每日数量：5 段
每段停留：60 秒
开机启动：开启
全屏或勿扰时暂停：开启
```

完成后进入托盘，主界面可关闭。

## 六、“完整又简洁”的内容拆分

### 6.1 不把“凝练”理解为改写原文

每张卡片分两层：

#### 原文层

- 必须忠实保存。
- 不允许模型重写后冒充作者原文。
- 在所有 UI 中优先级最高。

#### 辅助理解层

可以由 AI 生成，但必须明确标注：

- 本段标题。
- 上文承接。
- 一句话理解。
- 关键词。
- 预计阅读时间。

### 6.2 “完整”的技术定义

完整不是所有书都“一章一卡”，而是：

> 每个片段是一个语义完整的小单元，并且整本书正文不存在漏段、乱序和重复。

每个片段至少保存：

```text
source_id           来源文件
chapter_id          所属章节
block_start         起始正文块
block_end           结束正文块
source_anchor       EPUB CFI、PDF页码或DOM位置
original_text       原文
content_hash        原文指纹
sequence            阅读顺序
estimated_seconds   预计阅读秒数
parser_version      解析器版本
```

每个正文块应恰好被一个阅读片段覆盖。后续更换模型或重新生成标题时，不影响原文。

### 6.3 不同内容采用不同策略

| 内容类型 | 推荐阅读单元 | 大致长度 |
|---|---|---:|
| 《道德经》、诗词、箴言 | 自然章或完整条目 | 20～150 字 |
| 商业、管理、社科 | 小标题 + 1～3 个相关段落 | 100～300 字 |
| 小说、散文 | 完整场景或连续段落组 | 180～450 字 |
| 技术文档 | 一个概念、说明与完整列表 | 100～400 字 |
| 网页文章 | 小标题下的一个观点单元 | 100～300 字 |
| 超长段落 | 完整句号或语义转折处 | 20～90 秒 |

用户设置的是预计阅读时间，而不是生硬字数。

### 6.4 拆分管线

#### 第一步：结构解析

提取并标准化：

- 标题和目录。
- 正文段落。
- 引用和列表。
- 代码块。
- 图片说明。
- 脚注。
- 页码、CFI 或 DOM 定位。

#### 第二步：确定性规则

- 章节标题是强边界。
- 句号、问号和感叹号是候选边界。
- 列表不能从中间切断。
- 标题不能单独成为一张卡。
- 引用与解释尽量放在一起。
- 很短连续段落自动合并。
- 很长段落在完整句子后切开。

#### 第三步：AI 边界校正

模型接收带编号的正文块：

```json
[
  {"id":"b101","type":"heading","text":"第一节"},
  {"id":"b102","type":"paragraph","text":"……"},
  {"id":"b103","type":"paragraph","text":"……"}
]
```

模型只返回块的组合和辅助字段：

```json
{
  "segments":[
    {
      "block_ids":["b101","b102","b103"],
      "title":"……",
      "context_bridge":"上文谈到……",
      "explanation":"本段主要说明……"
    }
  ]
}
```

AI 可以建议哪些块组成一段，但不能自由生成替代原文。

#### 第四步：质量校验

- 是否有漏掉的正文块。
- 是否有重复正文。
- 是否从一句话中间切开。
- 标题后是否没有正文。
- 卡片是否过长或过短。
- 来源位置是否可重新打开。
- AI 解释是否明显失真。

## 七、阅读弹窗

示意：

```text
┌────────────────────────────────────────┐
│ 道德经 · 第一章                 1 / 81 │
│ 预计阅读 32 秒 · 第一章                │
│                                        │
│ 道可道，非常道；名可名，非常名……      │
│                                        │
│ ▸ 一句话理解                           │
│                                        │
│ [30分钟后]       [读完，下一段]         │
│             展开连续阅读               │
│ 48 秒后自动收起 · 鼠标悬停暂停         │
└────────────────────────────────────────┘
```

### 7.1 不抢焦点

弹窗出现时，不主动夺走用户正在输入的 Word、Excel、IDE 或聊天软件焦点。

### 7.2 默认无声音

除非用户主动打开系统通知，否则完全静音。

### 7.3 悬停暂停

鼠标进入卡片代表用户正在阅读，倒计时暂停；移出后继续。

### 7.4 自动关闭不等于已读

- 已展示：卡片出现。
- 已确认阅读：用户主动点“读完，下一段”或在连续阅读器中确认。

### 7.5 连续阅读不进入复杂后台

第一次继续直接切换下一段。用户想读更多时，展开右侧阅读面板，提供目录、上下文、笔记和进度。

### 7.6 暂停始终明显

至少支持：

- 10 分钟后。
- 30 分钟后。
- 午休后。
- 今天不再提醒。
- 暂停所有提醒。

## 八、主界面信息架构

主界面只保留：

```text
今天
书架
阅读计划
收藏与笔记
设置
```

### 8.1 今天

展示：

- 今日计划、已展示、已确认和阅读时间。
- 当前书籍与下一段。
- 接下来几段队列。
- 下一次提醒时间。
- 今日提醒节奏。
- 安静规则状态。

### 8.2 书架

- 显示来源而非复杂文件系统。
- 书籍、文档、网页统一为“阅读来源”。
- 查看解析片段和进度。
- 继续阅读。
- 导入新来源。

### 8.3 阅读计划

- 周几运行。
- 每日数量。
- 多个允许时段。
- 目标阅读时长。
- 弹窗停留时长。
- 未来提醒预览。
- 智能暂停。

### 8.4 收藏与笔记

- 保留完整原文。
- 保留书籍、章节和锚点。
- 用户笔记与原文分开。
- 支持 Markdown 导出。

### 8.5 设置

- 开机启动、关闭到托盘、系统通知。
- 主题、字体、字号、动画。
- AI Provider 配置，但不保存明文密钥。
- 本地数据导出与重置。

## 九、功能优先级

### P0：首版

| 模块 | 必须能力 |
|---|---|
| 桌面端 | Windows 10/11 |
| 输入 | 原生 TXT/Markdown；外部 Agent 生成的 `.tanyue.json` |
| 解析 | TXT/Markdown 本地解析；复杂格式由 Agent 处理 |
| 拆分 | 本地文本按规则拆分；Agent 包必须提供连续范围并接受完整性复核 |
| AI | 可选标题、承接、解释 |
| 卡片 | 自动弹出、倒计时、悬停暂停、关闭 |
| 操作 | 下一段、稍后、连续阅读、回原文 |
| 计划 | 工作日、时段、数量、停留、勿扰 |
| 系统 | 托盘、开机启动、关闭到托盘、休眠恢复 |
| 进度 | 已展示、已确认、位置、整书进度 |
| 数据 | 默认本地，SQLite |
| 安全 | 不内置密钥、不执行电子书脚本、不绕过 DRM |

### P1：跑通后

- 多书轮换。
- 根据关闭和连续阅读调整频率。
- 全屏、演示、勿扰、会议暂停。
- 完整阅读面板、搜索和目录。
- 每日回顾。
- 收藏、笔记和导出。
- macOS 和 Linux。
- Agent 导入预览和更清晰的失败诊断。

### P2：产品化

- 可替换的外部 Agent 工作流模板，但不建设专用 Skill/MCP 服务。
- 更多电子书格式。
- 多设备同步。
- 移动端。
- 收藏片段间隔复习。
- 账号、订阅和 AI 用量。
- 企业培训与制度资料微阅读。

## 十、推荐技术方案

```text
Tauri v2
TypeScript
SQLite
Source Adapter 解析层
Segmenter 拆分引擎
Scheduler 调度状态机
可替换 AI Provider
```

当前工程为了降低起步成本，前端使用原生 DOM + TypeScript + CSS，避免先引入大型前端框架。后续如果复杂度确实增长，可以在保持领域包不变的前提下迁移视图层。

## 十一、系统调度

不要只用永久 `setInterval`。必须持久化：

```text
next_due_at
last_shown_at
daily_shown_count
snooze_until
paused_until
active_schedule_id
```

以下事件都重新计算：

- 软件启动。
- 从休眠恢复。
- 修改计划。
- 延后提醒。
- 勿扰变化。
- 日期变化。

必须遵守：

- 错过的提醒不补弹。
- 开机和休眠恢复后留缓冲期。
- 多屏默认当前活动屏幕。
- 全屏演示不弹。
- 连续关闭时降低频率。
- 连续阅读可临时多读，但不制造额外自动提醒。

## 十二、AI 接入

### 个人原型

用户自填模型地址和密钥，密钥进入操作系统安全存储。

### 商业产品

```text
桌面端
  ↓ 登录和请求
自有 API 服务
  ↓ 鉴权、脱敏、限额、审计
外部模型 API
```

桌面安装包禁止包含公司模型密钥。

AI 只做：

1. 块组合边界建议。
2. 短标题和上文承接。
3. 明确标注的辅助解释。

AI 不做：

- 重写整本书冒充原文。
- 自由删除“不重要”内容。
- 生成没有来源锚点的摘要。
- 制造引文或作者观点。

缓存键至少包含：原文指纹、提示词版本、模型版本。

## 十三、首版验收

1. 《道德经》81 章顺序正确，无缺失和重复。
2. 重启后接续正确章节。
3. 弹窗不抢正在输入应用的焦点。
4. 默认按预计阅读时长自适应关闭，并支持 15～90 秒固定时间。
5. 悬停暂停倒计时。
6. 下一段、延后、今天暂停、展开阅读可用。
7. 休眠恢复不集中弹历史提醒。
8. 关闭主窗口后在托盘运行。
9. 关闭开机启动后无残留。
10. 每段能追溯原文。
11. 导入失败说明扫描、加密、空正文等原因。
12. 安装包、日志和数据中无模型密钥。
13. 电子书脚本不能执行。
14. 删除来源可选择同步删除解析与 AI 缓存。

## 十四、开发顺序

### 第一阶段：纵向样板

```text
导入《道德经》
→ 识别 81 章
→ 设置每日 5 次
→ 托盘定时弹窗
→ 继续/延后/自动关闭
→ 重启准确接续
```

### 第二阶段：三类内容

- 天然短章节的经典。
- 现代非虚构长段落。
- 外部 Agent 转换的网页文章或文字型 PDF 标准包。

### 第三阶段：产品化

- Agent 标准包的导入预览、错误定位和协议兼容升级。
- AI 标题与解释。
- 收藏和回顾。
- 安装签名、升级、崩溃恢复。
- 多书轮换。

## 十五、最终方向

不要 fork 一个完整阅读器再删功能。更干净的路径是：

- 新建轻量 Tauri 应用。
- 使用成熟开源库解决格式解析和定位。
- 自己掌握内容标准化、拆分算法、调度状态机和微阅读体验。
- 先把《道德经》纵向链路做透，再扩格式。
