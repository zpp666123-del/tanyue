# Windows 工程门禁与正式文本导入基础：需求规格

## 1. Goal

让“弹阅”在 Windows 上具备可重复执行的前端质量门禁，并将 TXT/Markdown 导入升级为遵循统一适配器、可证明全量覆盖、具备版本追溯信息的正式纵向链路。

## 2. 用户故事

1. 作为开发者，我希望在全新 Windows 环境安装依赖后运行一条命令即可完成类型检查、测试和构建，从而可靠判断提交是否可交付。
2. 作为读者，我希望 TXT/Markdown 的每个可阅读正文块都被且只被一个片段覆盖，从而不会漏读、重复或乱序。
3. 作为维护者，我希望每次导入都记录解析器和拆分规则版本，从而可以定位历史数据由哪套逻辑生成。
4. 作为读者，我希望导入失败或完整性不合格时看到明确原因，并且不把不合格内容静默写入书架。

## 3. 验收标准

### R1：Windows 可重复验证

- 在已安装 Node.js 20+ 且完成 `npm install` 的 Windows 环境中，当执行 `npm run verify` 时，系统应完成 TypeScript 严格检查、自动化测试、静态构建和工程结构检查，并以退出码 0 结束。
- 当任一检查失败时，验证命令应返回非零退出码，并输出可定位到阶段和原因的错误信息。
- 构建与测试脚本在 Windows、macOS 和 Linux 上计算项目路径时，均不得生成重复盘符或错误根目录。
- 项目应提交 npm 锁文件，使依赖安装可重复。

### R2：统一文本来源适配器

- 当用户导入 TXT 或 Markdown 文件时，系统应通过 `SourceAdapter` 接口完成检测和解析，不得由 UI 点击事件直接包含解析规则。
- `SourceAdapter` 应暴露稳定的适配器标识和版本，并输出统一的 `NormalizedDocument` 与带来源锚点的正文块。
- 当输入为空、格式不受支持或解析失败时，适配器应返回明确的失败原因。
- TXT/Markdown 适配器不得执行输入内容中的脚本或活动内容。

### R3：全量覆盖与顺序

- 当标准化文档被拆分时，系统应生成覆盖率报告，且每个可阅读正文块的引用次数必须恰好为 1。
- 当覆盖率不是 100%、存在重复引用、顺序异常或空片段时，导入结果应判定为失败，不得加入应用状态。
- 每个成功导入都应包含可供 UI 或日志展示的覆盖率、重复数、片段数和正文块数。
- 对超过单片目标长度的正文块进行句子级拆分时，系统仍应能够证明该块内容完整且顺序不变。

### R4：追溯信息

- 每个成功生成的片段应记录 `bookId`、连续 `sequence`、`sourceAnchor`、`contentHash`、解析器版本、拆分器版本和规则版本。
- 当未来 AI 处理实际发生时，系统应能够记录提示词版本与模型版本；本轮未调用 AI 时，这两项应显式为空或未应用，不得伪造值。
- 追溯字段应属于领域模型，不得只存在于 UI 文案或临时日志中。

### R5：测试门禁

- 自动化测试应覆盖：空文件、普通 TXT、Markdown 标题、多段合并、超长段拆分、重复原文、覆盖率 100%、顺序连续和追溯字段。
- 自动化测试应覆盖 `shown` 不会变成 `confirmed`，只有显式确认才改变确认状态。
- 《道德经》81 章测试应继续通过，并验证无漏段、无重复、顺序连续。
- 新增领域行为必须由测试直接验证，不能只通过搜索构建产物中的字符串来证明。

### R6：状态与文档一致

- 完成实现后，当执行全部门禁时，`PROJECT_STATUS.md` 应记录真实执行结果、当前环境未验证项和下一阶段边界。
- 项目文档不得声称尚未执行或当前失败的检查已经通过。

## 4. 约束

- 保持 Tauri v2、TypeScript、原生 DOM/CSS，不引入前端框架。
- 保持领域逻辑与 UI 分离。
- `Segment.originalText` 只能来自标准化后的原文块，AI 结果不得覆盖它。
- 不内置 API Key，不默认上传原文，不执行导入内容中的脚本。
- 第三方解析器若后续加入，必须通过 `SourceAdapter` 封装。

## 5. 本轮不改范围

- 不实现 SQLite、LocalStorage 迁移或数据库备份；这是下一独立 Goal。
- 不实现 EPUB、PDF、DOCX 或正式网页 Readability 适配器。
- 不改现有视觉设计和页面信息架构。
- 不实现 AI Provider。
- 不宣称完成 Tauri 真机验证；只有安装 Rust 并实际通过相关命令后才能更新该状态。
- 不处理安装包签名、自动升级、商标或应用商店发布。
